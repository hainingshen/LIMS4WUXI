# 部署与发布手册

## 1. 文档定位

本手册描述 LIMS4WUXI 一期生产部署形态、Nginx 拓扑、CI/CD 流水线、蓝绿发布、备份恢复和等保二级合规检查。本文与 [00_技术栈与工程约定.md](00_技术栈与工程约定.md)、[05_数据迁移与实施边界.md](05_数据迁移与实施边界.md)、[13_迭代里程碑与上线切换.md](13_迭代里程碑与上线切换.md) 联动。

## 2. 部署形态

部署形态：**公有云 ECS 私有部署，自建数据库与对象存储，等保二级**。

| 资源 | 选型 | 数量 | 配置参考 |
| --- | --- | --- | --- |
| 应用服务器 | 阿里云或华为云 ECS（按客户选定）| 2 台 | 8 vCPU / 16 GB / 200 GB SSD，私有 VPC |
| 数据库服务器 | 自建 PostgreSQL 16 on ECS | 1 主 + 1 备 | 8 vCPU / 32 GB / 1 TB SSD，主备流复制 |
| 对象存储 | 自建 MinIO on ECS | 1 主 + 1 备份镜像 | 4 vCPU / 16 GB / 2 TB SSD |
| 文档服务 | OnlyOffice Document Server on ECS | 1 台 | 4 vCPU / 8 GB |
| 缓存 | Redis Sentinel | 3 节点哨兵 | 2 vCPU / 4 GB |
| 反向代理 | Nginx | 与应用同机 | 与 backend 共 ECS |

**不使用云厂商 RDS**：客户合规要求数据可完整导出和审计，自建 PG 便于备份导出和故障定位。

## 3. Nginx 拓扑

单域名 + 路径分流，单证书，同源 Cookie。

```text
https://lims.client.example.com/
  /portal/...     →  web-portal (静态)
  /internal/...   →  web-internal (静态)
  /m/...          →  PWA 移动入口（响应式与桌面端共代码，软链不同 index.html）
  /api/v1/...     →  backend (upstream blue/green)
  /files/...      →  MinIO 代理（带签名 URL 校验）
  /docs/...       →  OnlyOffice 文档服务（仅内网，外网通过 backend 中转）
```

关键约定：

- HTTP 一律 301 重定向 HTTPS。
- 静态文件加 ETag 和 Cache-Control，构建产物文件名带 hash。
- `/api/v1/` upstream 配置 `backend-blue` 和 `backend-green` 两组，蓝绿切换通过 `nginx -s reload` 或 `set_upstream` 动态调整。
- `/files/` 走 MinIO 预签名 URL，URL 中包含过期时间和签名，过期立即失效。
- WAF 启用基础规则：SQL 注入、XSS、命令注入；TLS 仅允许 1.2+。

Nginx 关键片段示例：

```nginx
upstream lims_backend_blue { server 10.0.1.11:8080; }
upstream lims_backend_green { server 10.0.1.12:8080; }

map $upstream_label $lims_backend {
  default lims_backend_blue;
  green   lims_backend_green;
}

server {
  listen 443 ssl http2;
  server_name lims.client.example.com;

  location /api/v1/ {
    proxy_pass http://$lims_backend;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_read_timeout 120s;
  }

  location /portal/ { root /var/www/lims; try_files $uri /portal/index.html; }
  location /internal/ { root /var/www/lims; try_files $uri /internal/index.html; }
  location /m/ { root /var/www/lims; try_files $uri /m/index.html; }
}
```

## 4. 部署单元与容器化

每个部署单元独立 Docker 镜像。Compose 起步，二期视情况上 K8s。

当前仓库提供根目录 `docker-compose.yml` 作为私有化部署起步基线，敏感配置从 `.env` 读取：

```bash
cp .env.example .env
docker compose up -d --build
curl -i http://localhost:8080/api/v1/auth/me
```

Compose 包含 PostgreSQL、Redis、MinIO、OnlyOffice、backend 和 Nginx。Nginx 暴露 `http://localhost:8080/internal/`、`/portal/` 和 `/api/v1/*`，backend 启动时自动执行 Flyway。蓝绿发布时保留本节原定策略：将 `backend` 拆成 `backend-blue`、`backend-green` 两个同配置服务，由 Nginx upstream 切换。

## 5. CI/CD 流水线

当前仓库已落地 `.github/workflows/backend-verify.yml` 作为合并前质量门禁：每个 PR 和 `main` push 都运行规格校验、后端测试和前端 TypeScript 校验。发布阶段仍按 backend、web-internal / web-portal、specs 三类流水线拆分，互不阻塞。

### 5.0 当前合并前门禁

1. 安装 Python 校验依赖。
2. 运行 `python scripts/checks/csv-foreign-key.py`。
3. 运行 `python scripts/checks/drift-detector.py`。
4. 使用 Node 20 + pnpm 9.15.9 安装 workspace 依赖。
5. 运行 `pnpm -r typecheck`。
6. 进入 `backend/` 运行 `mvn test`。

### 5.1 backend 流水线

1. PR 合并到 `main` 触发。
2. Maven 构建 + Spotless + Checkstyle。
3. JUnit 5 + Testcontainers 集成测试。
4. OpenAPI 校验：`openapi-generator validate -i specs/openapi.yaml`。
5. Docker 镜像打 tag = `${gitShortSha}-${timestamp}`，推送私有 registry。
6. 部署阶段：
   - 推送到 `backend-green` 容器，重启。
   - 健康检查 `/api/v1/ops/health` 通过。
   - Nginx upstream 切换到 green。
   - 观察 5 分钟，无异常将 `backend-blue` 也同步镜像。

### 5.2 web-internal / web-portal / web-mobile 流水线

1. PR 合并触发。
2. `pnpm install` + ESLint + Prettier + TypeScript strict 校验。
3. Vitest 单元测试 + Playwright E2E 关键路径。
4. `pnpm build` 输出到 `dist/`。
5. 上传到部署机的 `/var/www/lims/{portal|internal|m}.new/`，原子软链切换。
6. CDN 缓存清理（如启用 CDN）。

### 5.3 specs 流水线

每次 PR 改动 `specs/*.csv` 或 `specs/openapi.yaml` 触发：

1. 运行 `python -m pip install -r scripts/checks/requirements.txt`。
2. 运行 `python scripts/checks/csv-foreign-key.py`：校验 roles ↔ permission_matrix、字典引用、送检单字段锁定策略、OpenAPI `$ref` 和 demo fixture。
3. 运行 `python scripts/checks/drift-detector.py`：校验 `07_API与界面契约.md`、`10_工作中心详细设计.md` 与 `specs/openapi.yaml` 不漂移，并校验 Markdown 内链和前端路由角色。
4. 如 CI 环境已安装 Spectral 或 openapi-generator，再追加 OpenAPI lint。
5. 通过后 PR 才可合并。

## 6. 蓝绿部署 SOP

### 6.1 后端蓝绿

```
当前流量在 blue，要发新版本：
1. 停止 backend-green 容器
2. docker-compose pull backend-green
3. docker-compose up -d backend-green
4. 等待 /api/v1/ops/health 200，且 database/objectStorage 均为 UP
5. nginx 配置 $upstream_label=green，nginx -s reload
6. 监控 5 分钟（错误率、P99、付款门禁审计日志）
7. 通过则 docker-compose pull backend-blue，更新 blue 至同版本
8. 不通过则 nginx 切回 blue，标记此次发布失败
```

### 6.2 前端

```
1. pnpm build 产物上传到 /var/www/lims/internal.new/
2. ln -sfn /var/www/lims/internal.new /var/www/lims/internal
3. nginx 无需 reload（仅静态文件）
4. 用户下一次刷新页面采用新前端
5. 如需回滚 ln -sfn /var/www/lims/internal.old /var/www/lims/internal
```

## 7. 数据库迁移

Flyway 管理。一期约定：

- 所有结构变更必须通过 Flyway 脚本，禁止手工 `ALTER TABLE`。
- 脚本命名 `V{yyyyMMddHHmm}__{descriptive_snake_case}.sql`。
- 生产部署前 PR 必须包含迁移脚本及其回滚预案。
- 历史数据迁移走单独的 `migration` 模块，结果写入业务表的 `legacy_id` / `source_type` / `data_quality_score` 字段，见 [05 §4.1](05_数据迁移与实施边界.md)。

## 8. 备份与恢复

| 资产 | 备份方式 | 频率 | 保留 |
| --- | --- | --- | --- |
| PostgreSQL | `pg_basebackup` 全量 + WAL 流复制 + 每日 `pg_dump` 逻辑备份 | 全量周 + 增量日 | 6 年 |
| MinIO | 按桶镜像到异地 OSS/COS（客户提供）| 每日 | 6 年 |
| 配置 / 密钥 | 部署机本地 `/etc/lims/` 加密备份 | 每周 | 永久 |
| BPMN / DOCX 模板 | MinIO 同步规则 | 实时 | 6 年 |
| 审计日志 `audit_log` | 与 PG 同方案，额外冷备 | 与 PG 一致 | 永久 |

本地 compose 环境提供可执行基线脚本：

```bash
scripts/ops/backup-compose.sh
```

脚本输出到 `backups/{UTC时间戳}/`：

- `postgres.dump`：PostgreSQL 自定义格式逻辑备份，可用 `pg_restore --clean --if-exists` 恢复。
- `minio-lims-files.tar.gz`：`lims-files` 桶对象归档，可解压后用 `mc mirror` 恢复。
- `README.restore.md`：本次备份对应的恢复命令。

生产环境必须把同等流程固化到客户指定的备份介质，并满足：

- 每日自动生成 PG 逻辑备份和 MinIO 桶镜像。
- 每周抽检一次备份文件可读取。
- 每季度演练一次 PG 全量恢复 + MinIO 部分恢复，结果写入档案。
- 恢复后必须执行 `scripts/ops/health-check.sh` 和最小业务 smoke，确认数据库、对象存储、登录、报告下载链路可用。

## 9. 监控与告警

| 维度 | 工具 | 关键指标 |
| --- | --- | --- |
| 应用 | `/api/v1/ops/health` + Prometheus + Grafana | 数据库可用性、对象存储可用性、JVM、HTTP P99、错误率、Flyway 失败、JDBC 连接池 |
| 数据库 | pg_exporter | 慢查询、连接数、复制延迟、磁盘 |
| 缓存 | redis_exporter | 内存、慢命令、Pub/Sub 滞后 |
| 对象存储 | MinIO 自带 metrics | 桶大小、错误请求 |
| 业务 | 自研业务指标 | 报告生成失败、付款门禁误拦截、审批超时 |
| 安全 | 审计日志 + 告警规则 | 异常登录、权限越权、文件批量下载 |

告警通道：钉钉 / 企业微信 / 邮件三选一，由客户指定。

健康检查和追踪要求：

- 部署后执行 `scripts/ops/health-check.sh`，该脚本请求 `/api/v1/ops/health` 并校验 `status=UP`、`checks.database=UP`、`checks.objectStorage=UP`。
- 所有 HTTP 响应都应携带 `X-Trace-Id`，日志、审计和报告发放日志需要保留该关联 ID。
- 报告发放问题定位使用 `scripts/ops/trace-report-delivery.sh <report_id>`，输出报告版本、文件对象、发放日志和同 trace 的审计记录。
- 运维排障记录必须写明 traceId、用户、报告号、文件对象 key、发放类型和处理结果。

## 11. 配置与密钥管理

- 应用配置：`application-{env}.yml` 按 Spring Profiles 切换。
- 密钥：通过环境变量注入，不入 Git。
- 密钥来源：客户自有 KMS 或 HashiCorp Vault（一期可降级为加密的 `.env` 文件，由系统管理员维护）。
- 数据库密码、MinIO Access Key、Redis 密码、JWT 签名密钥每 90 天轮换一次。

## 12. 上线切换步骤（一期首次上线）

详细步骤承接 [13_迭代里程碑与上线切换.md](13_迭代里程碑与上线切换.md) §3，本文补充技术细节：

1. 客户提供生产环境 ECS、域名、SSL 证书、私有 registry 凭证。
2. 部署基础组件：PostgreSQL 主备、Redis Sentinel、MinIO、OnlyOffice、Nginx。
3. 初始化数据库：执行 Flyway 全部脚本。
4. 灌入种子数据：roles、permission_matrix、dictionaries、test_catalog、form_schema 初始版本。
5. 按 [05 §6 迁移实施步骤](05_数据迁移与实施边界.md) 执行历史数据迁移。
6. 部署 backend-blue 镜像，启动并健康检查。
7. 部署前端静态文件。
8. Nginx 配置生效，将 upstream 指向 blue。
9. 内部 UAT 验收 [13 §4 最小验收脚本](13_迭代里程碑与上线切换.md)。
10. 客户验收。
11. 切换正式域名，启用监控告警。
12. 上线后第一周每日核对付款门禁、报告发放、样品流转、工作中心预警。

## 13. 回滚预案

| 场景 | 回滚动作 |
| --- | --- |
| 后端发布出错 | Nginx upstream 切回 blue，触发告警 |
| 前端发布出错 | 静态文件软链切回 `.old` |
| 数据库迁移失败 | Flyway 提供反向脚本；如不可逆，从最近备份恢复并屏蔽相关功能 |
| 数据被误改 | 通过 `audit_log` 定位，用 `before_snapshot` 还原；如范围大，DB 回滚到时间点 |
| 关键组件不可用 | 切到客户指定的灾备 ECS，按备份恢复数据库和 MinIO |

回滚演练频率：上线前 1 次全流程演练，上线后每半年 1 次。

报告下载或发放异常排查顺序：

1. 用用户反馈的 traceId 查询应用日志。
2. 用报告 ID 执行 `scripts/ops/trace-report-delivery.sh <report_id>`。
3. 核对 `report_delivery_log` 的发放类型、付款门禁状态、文件 ID 和对象 key。
4. 核对 `audit_log` 中同 trace 的权限判断、状态机动作和异常原因。
5. 如文件对象缺失，先从最近 MinIO 备份恢复单对象，再重新执行报告下载 smoke。
