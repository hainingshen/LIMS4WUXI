# 技术栈与工程约定

## 1. 文档目的

本文档用于约束后续 Vibe Coding 和人工开发的一致性。未被本文档修改前，代码生成不得自行更换框架、字段命名、目录结构、状态机实现方式、规则引擎或报告渲染方案。

本文综合 [13_迭代里程碑与上线切换.md](13_迭代里程碑与上线切换.md)、[16_部署与发布手册.md](16_部署与发布手册.md)、[17_修改生效SLA与可配置项清单.md](17_修改生效SLA与可配置项清单.md) 和 [18_第四轮决策记录.md](18_第四轮决策记录.md) 一并使用。

## 2. 技术栈基线

| 层级 | 选型 | 约定 |
| --- | --- | --- |
| 后端 | **Java 17 LTS + Spring Boot 3.3.x** | 模块化单体，按业务域拆包，一期不拆微服务 |
| ORM | **Spring Data JPA + Hibernate + QueryDSL** | 实体注解式建模；复杂查询走 QueryDSL；迁移脚本和报表可降级到 Native SQL |
| 数据库 | **PostgreSQL 16 + Flyway** | 自建于客户公有云 ECS，不使用云厂商 RDS |
| 工作流 | **手写状态机 + `approval_record` + `business_rule`** | 不引入 Flowable；审批节点用领域事件 + Aviator 规则表达式 |
| 规则引擎 | **Aviator** | 用于业务条件判断和简单动作；不引入 Drools/Groovy 脚本 |
| 前端框架 | **React 18 + TypeScript + Vite** | 桌面端、客户门户、移动端共用 React 体系 |
| 桌面 UI 库 | **Ant Design 5** | 复杂表单、表格、审批、日历 |
| 移动 UI 库 | **Ant Design Mobile 5** | 与 AntD 5 共享设计令牌 |
| 动态表单 | **formily 2.x** | 送检单、原始记录、报告草稿表单按 `form_schema` 渲染 |
| 状态管理 | **Zustand** | 全局用户、权限、字典、筛选条件 |
| 数据请求 | **Axios + TanStack Query** | 拦截鉴权、错误码；缓存、重试、失效 |
| 移动端形态 | **响应式 PWA** | React + AntD/AntD Mobile 一套代码两端跑；二期视需求用 Capacitor 套壳 |
| 鉴权 | **JWT Access Token + Refresh Token + Redis 黑名单** | Access TTL 15 分钟，Refresh TTL 7 天；登出、强制下线、角色变更写入黑名单 |
| 权限 | **RBAC + 数据范围** | 一人多角色，数据按委托单位/项目/工单隔离 |
| 文件存储 | **MinIO** | 自建于客户公有云 ECS；文件元数据入库，文件实体进对象存储 |
| 报告模板 | **DOCX 模板 + poi-tl 渲染** | 模板按 `template_code + template_version` 存 MinIO，后台可上传新版本 |
| 文档服务 | **OnlyOffice Document Server** | DOCX 在线预览、编辑、转 PDF；与 backend 内网调用 |
| 电子签章 | 签章适配接口 | 一期预留接口，正式接入客户确认的 CA/电子章服务 |
| 缓存 | **Redis 7 + Redisson** | 令牌黑名单、字典缓存、分布式锁、通知未读数；Pub/Sub 用于配置失效广播 |
| 国际化 | **react-i18next** | 前端文案多语言；报告模板按 `report_language` 选 zh/en 模板 |
| 日志 | Logback + JSON 日志 + `audit_log` 表 | 关键业务操作通过 AOP 异步写审计表 |
| 部署 | Docker Compose 起步 | backend 蓝绿、postgres、minio、redis、onlyoffice、nginx 独立容器 |
| 部署形态 | 公有云 ECS 私有部署 | 等保二级；自建 PG/MinIO；详见 [16](16_部署与发布手册.md) |

| 数据库字段 | `snake_case` |
| Java 类 | `PascalCase` |
| Java 字段 | `camelCase` |

## 5. ID 与编号

系统采用双轨标识：

- 技术主键：UUIDv7，字段名 `id`，所有表统一。
- 业务编号：字段名 `biz_no`，用于页面展示、搜索、报告和客户沟通。

编号规则：

| 报价 | `Q-{yyyy}-{seq4}` | `Q-2026-0001` |

## 7. 工作流实现约定

一期不引入 Flowable BPMN 引擎。所有审批用 **业务实体状态机 + `approval_record` 表 + 领域事件 + Aviator 规则** 实现。

### 7.1 状态机与领域事件协作

业务状态唯一可信源是业务实体状态字段（如 `project.status`、`report.status`、`study_plan.status`）。审批人、候选人、审批历史在 `approval_record` 表中持久化。审批节点之间的跳转由业务服务驱动，状态变更后通过 Spring `ApplicationEventPublisher` 发布领域事件，下游订阅者执行联动动作。

通用约定：

1. 控制器只接收审批请求，不直接迁移状态。
2. 领域服务校验权限和 guards，迁移状态并写 `approval_record`。
3. 发布领域事件（如 `ProjectNonstandardApprovedEvent`）。
4. 跨实体联动逻辑（见 06 §11）在事件监听器中执行。

非标评审示例：

```text
1. POST /projects/{id}/nonstandard-review/approve  { stage: TECH|BUSINESS, outcome, comment }
2. ProjectApprovalService.approve(projectId, stage, outcome, currentUser, comment)
   - 鉴权 + 校验当前 stage 可执行
   - 写 approval_record(stage=TECH, outcome=APPROVED, user=...)
   - 根据 stage 进度判断下一步：
       - TECH 通过 → 仍 NONSTANDARD_REVIEW，等待 BUSINESS
       - BUSINESS 通过 → status=QUOTABLE，发 ProjectQuotableEvent
       - 任一驳回 → status=ACCEPTED，发 ProjectNonstandardRejectedEvent
3. 监听器执行后续动作：通知销售、解锁报价、更新工作中心
```

### 7.2 业务规则与 Aviator

需要客户灵活调整的判断逻辑（如"GLP 必走 QA"、"动物试验必走伦理"、"两天无进展告警"）必须写入 `business_rule` 表（见 [06 §2.21](06_数据模型与状态机.md)），不写死在 Java 代码里。

约束：

- `condition` 是 Aviator 表达式字符串，输入上下文为业务实体的 JSON。
- `action` 是动作 DSL 或预定义 actionCode，引用 `permission_matrix.csv` 中的 actionCode。
- 表达式求值在 `RuleEngineService.evaluate(ruleCode, context)` 内集中执行，控制器或其他服务不得直接调用 Aviator API。
- 修改规则只动 `business_rule` 表，不重启 backend；Redis Pub/Sub 通知失效缓存。

## 8. 报告生成约定

一期报告生成流程：

结构化数据 → DOCX 模板渲染（poi-tl）→ 草稿 DOCX → 人工编辑和审核 → 正式 DOCX 锁定 → OnlyOffice 转 PDF → 电子签章 → 发放。

约束：

- 草稿必须带水印。
- 正式 PDF 生成前必须通过报告审核。
- 正式 PDF 下载受付款门禁控制。
- 报告模板字段必须来自字段映射表，不允许模板里临时写数据库字段名。
- 模板按 `template_code + template_version` 存 MinIO；后台可上传新版本，新请求自动用新版本，进行中请求仍用旧版本。
- 每次正式报告生成都要保存模板版本、数据快照（`data_snapshot_file_id`）和渲染日志。

## 9. 元数据驱动表单

送检单 / 原始记录 / 报告草稿 / 系统参数等表单**必须**通过 [`form_schema`](06_数据模型与状态机.md) 表运行时加载，前端用 **formily 2.x** 渲染。

约束：

- 字段定义、必填、字典引用、`lock_policy`、联动校验全部声明在 `form_schema.schema_json` 中。
- 新增字段 = 新版本 `form_schema` 发布 + Redis 失效广播；不重启 backend、不发版前端。
- 硬编码字段视为缺陷。Vibe Coding 在 PR 阶段必须校验 form_schema 来源。
- 初始 schema 从 [`specs/submission_ver15_fields.csv`](specs/submission_ver15_fields.csv) 转换得到，作为 v1 种子。

## 10. 客户门户与移动端鉴权

### 10.1 JWT 结构

```
Access Token (JWT, HS256 或 RS256)
  payload: { sub, jti, clientType, roles[], orgId?, exp, iat }
  TTL: 15 分钟（系统参数 AUTH_ACCESS_TOKEN_TTL_MINUTES 可调）

Refresh Token (随机字符串)
  存 Redis: refresh:{jti} → { userId, clientType, expiresAt }
  TTL: 7 天（系统参数 AUTH_REFRESH_TOKEN_TTL_DAYS 可调）

Token 黑名单
  Redis Set: blacklist:access、blacklist:refresh
  写入场景：登出、强制下线、用户角色变更、密码修改、明显异常登录
```

### 10.2 客户侧角色

- `CUSTOMER_ORG_ADMIN`：管理本委托单位用户，可查看本单位全部项目和报告。
- `CUSTOMER_APPLICANT`：提交送检信息，默认只查看本人提交项目。
- `CUSTOMER_VIEWER`：只读查看被授权项目。

一期客户门户采用邀请或内部创建账号，不开放匿名自注册。代理商或跨单位人员必须通过 `customer_agency_grant` 授权，不允许一个账号默认查看多个委托单位数据。

### 10.3 客户端类型

`clientType` 取值：

- `INTERNAL`：内部端 Web。
- `PORTAL`：客户门户 Web。
- `MOBILE`：响应式 PWA 在移动设备访问；与桌面端共享后端，但前端按断点切换 AntD / AntD Mobile 组件。

token 中固化 `clientType`，路由守卫和后端鉴权按该字段分流。`MOBILE` 与 `INTERNAL` 共用内部端权限矩阵，与 `PORTAL` 完全隔离。

## 11. 付款确认默认决策

一期不接银行流水和 ERP。付款状态由财务人员或出纳在系统内手工登记收款记录。

角色：

- `FINANCE_CASHIER`：登记到账、上传凭证、解锁付款门禁。
- `FINANCE_MANAGER`：复核异常收款、查看应收和绿色通道项目。

后续如接 ERP 或银行流水，只能写入收款记录表，不直接改报告状态。

## 12. 系统配置与可编辑项

凡是"客户可能希望快速调整"的参数都必须落到 `system_config` 表（见 [06 §2.22](06_数据模型与状态机.md)），不写死在代码里。完整可配置项清单见 [17_修改生效SLA与可配置项清单.md](17_修改生效SLA与可配置项清单.md)。

约束：

- 修改通过后台界面提交，由指定角色（如 `SYSTEM_ADMIN`、`QUALITY_MANAGER`）操作。
- 修改后写入 `audit_log`，Redis Pub/Sub 广播失效。
- Backend 通过 `SystemConfigService.get(key)` 读取，本地缓存 TTL 60 秒。

## 13. LLM 代码生成约束

每次生成代码前，必须读取：

- `00_技术栈与工程约定.md`
- `06_数据模型与状态机.md`
- `07_API与界面契约.md`
- `specs/openapi.yaml`
- `specs/roles.csv`
- `specs/permission_matrix.csv`
- `specs/dictionaries.csv`
- 当前任务涉及的业务文档

生成代码时必须遵守：

- 不新增未在文档中定义的状态。
- 不新增未在文档中定义的角色。
- 不改变接口字段命名风格。
- 不绕开手写状态机和 `approval_record` 流程。
- 不把付款门禁写死在前端。
- 不把客户权限只靠前端隐藏。
- 不把字典、阈值、审批人选择写死，必须读 `system_config` 或 `business_rule`。
- 不引入 Flowable、Drools、Groovy 脚本、Vue、Pinia、MyBatis 等已被本文档显式排除的依赖。
- 每个状态转移动作必须有单元测试或集成测试。
- 表单实现必须基于 `form_schema`，不允许整页硬编码字段。

## 15. Lint 与格式化

后端：

- Maven Spotless + Checkstyle + ErrorProne。
- 禁止控制器直接访问 Repository；控制器只调领域服务。
- Flyway 脚本必须命名规范，PR 必须含回滚预案。

前端：

- ESLint + Prettier + TypeScript strict。
- API 类型由 `openapi-generator` 从 [`specs/openapi.yaml`](specs/openapi.yaml) 生成，不手写重复 DTO。
- formily schema 校验脚本：CI 阶段对 `form_schema.schema_json` 跑 JSON Schema 校验。

## 16. 部署与发布

详见 [16_部署与发布手册.md](16_部署与发布手册.md)。本文不重复内容。简要约束：

- Nginx 单域名 + 路径分流；HTTP 一律 301 HTTPS。

- 等保二级合规检查清单见 16 §10。
