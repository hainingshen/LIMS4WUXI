## 2. 总体结论

当前系统尚未完成设计文档定义的“客户送检信息 → 内部受理 → 项目类型判断 → 报价前评审 → 报价 → 合同/协议签署 → 样品接收 → 样品入库 → 方案编制 → 审批 → 试验计划 → 试验下发 → 试验执行 → 结果录入 → 原始记录审核 → 报告编制 → 报告审核 → 付款控制 → 报告发放 → 样品处置 → 档案归档”主流程闭环。

当前更接近“登录 + 送检单 Ver.15 表单壳 + 工作中心空壳 + 部分接口骨架”。主要问题集中在：

- 客户门户只有首页、新建送检单、我的项目三个入口，缺少提交、项目进度、协议确认、报告草稿预览和正式报告下载闭环。
- 内部端按不同角色仅显示少量菜单，销售端只有工作中心、送检受理、项目详情；管理员端只有工作中心。大量文档约定页面未出现。
- 工作中心虽然有页面结构，但数据全部为 0 或空表，缺少可操作的阻塞、Owner、待办、趋势闭环。
- API 与 `openapi.yaml` 大量漂移：多条核心路径返回 404，合同列表返回 500，部分路径只有空数据。
- 客户门户 token 可以访问多个内部业务资源并返回 200 空结果，权限边界需要收紧。
- 内部端和门户在同一 origin 下共用登录状态，切换登录会互相覆盖会话。
- MinIO 控制台可达，但未提供 MinIO 账号，未能验证 bucket、模板、报告文件和上传归档链路。

## 3. 入口、鉴权和路由缺口

### 3.1 内部端与门户共用浏览器本地会话

应有能力：

- `INTERNAL` token 只能进入内部端路由。
- `PORTAL` token 只能进入客户门户路由。
- 内部端和门户应按 `clientType` 分流，互不污染登录态。

实测现状：

- 内部端和客户门户在同一 host/port 下运行，不同 path 共用浏览器 origin。
- 先登录门户后再登录内部端，客户门户刷新或访问直达路径会回到登录页。
- 这说明两端登录状态存在覆盖风险，至少当前测试体验无法同时保持两个端的会话。

缺口：

- 登录态存储需要按端隔离，例如 `lims.internal.auth.session` 与 `lims.portal.auth.session`。
- 后端仍需严格校验 `clientType`，不能只依赖前端隐藏。
- 刷新页面、直接访问深链、跨端切换时应保持符合预期的路由守卫行为。

### 3.2 前端路由没有按文档实现深链

应有能力：

- 文档定义了 `/portal/submissions/new`、`/portal/projects/:id`、`/portal/reports/:id/preview` 等门户路由。
- 文档定义了 `/internal/work-center`、`/internal/samples/receiving`、`/internal/master-data` 等内部路由。

实测现状：

- 内部端访问 `/internal/master-data`、`/internal/samples/receiving` 仍显示同一个工作中心页面。
- 客户门户直达 `/portal/submissions/new`、`/portal/projects/:id`、`/portal/reports/:id/preview` 未进入对应业务页。

缺口：

- 需要补齐 React Router 路由表，与 `07_API与界面契约.md` 中的路由清单一致。
- 菜单选中状态、浏览器 URL、刷新恢复、详情页参数解析都需要落地。

## 4. 客户门户缺口

### 4.1 客户首页

应有能力：

- 查看本人或本单位项目。
- 查看项目进度。
- 查看报告草稿。
- 付款后下载正式报告。
- 确认或签署协议。

实测现状：

- 客户首页仅显示三个卡片：客户首页、新建送检单、我的项目。
- 未展示项目编号、样品名称、项目状态、报告状态、提交日期等筛选或列表。
- 未展示待确认协议、草稿报告、付款门禁状态或正式报告下载入口。

缺口：

- 增加项目列表、状态筛选、当前节点、进度条、报告状态和协议待办。
- 增加客户侧数据范围：普通申请人默认只看本人提交项目，单位管理员看本单位全部项目，只读用户看授权项目。
- 首页应从真实 API 加载，不应停留在静态入口卡片。

### 4.2 新建送检单

应有能力：

- 按 Ver.15 8 个 PART 动态渲染结构化字段。
- 前后端必填校验一致。
- 字典从 `/dictionaries` 获取。
- 支持保存草稿和提交送检。
- 提交后进入内部受理。
- 支持必要附件，例如客户提供方法文件、送检单附件、特殊说明材料。

实测现状：

- 页面可以渲染 `SUBMISSION VER.15`，包含 PART1 到 PART8。
- 点击空表单“保存草稿”会触发大量必填校验。
- 页面只有“重置”和“保存草稿”，未看到“提交送检单”按钮。
- 未看到草稿列表、恢复草稿、提交后编号、提交成功提示和内部受理联动。
- 表单中出现“样品接收人”“样品接收日期”等更偏内部收样环节的字段，客户门户是否应填写需要重新核对。
- 未看到附件上传入口。

缺口：

- 明确草稿保存与正式提交的状态机：`DRAFT -> SUBMITTED`。
- 增加提交按钮并调用 `POST /submissions/{id}/submit`。
- 提交成功后显示送检单号、提交时间、当前状态和后续节点。
- 客户可填字段与内部收样字段需要拆分，不应把内部核验字段直接暴露给客户填写。
- 送检单数据应能在内部端送检受理列表出现。
- 需要支持附件上传、附件元数据、MinIO 对象存储和归档。

### 4.3 我的项目

应有能力：

- 展示本人项目、样品和报告。
- 展示项目进度和当前节点。
- 支持查看报告草稿。
- 付款后支持下载正式报告。
- 显示协议确认或签署状态。

实测现状：

- “我的项目”页面只有标题和一句说明：“查看项目、样品和报告”。
- 没有项目列表、详情、报告预览、下载按钮、付款状态或协议入口。

缺口：

- 增加项目列表和详情页。
- 增加报告草稿预览页，草稿必须带水印、不展示电子签章、不允许下载正式 PDF。
- 增加正式报告下载入口，后端必须二次校验付款门禁。
- 增加协议确认/签署入口和签署文件查看。

### 4.4 客户门户 API 权限边界

应有能力：

- 客户门户不能访问内部试验计划、工单、原始记录、付款登记、绿色通道、报告模板等内部资源。
- 客户只能访问本单位或本人授权范围内的数据。

实测现状：

- `portal.applicant` token 调用以下内部资源返回 200 空结果：`/study-plans`、`/work-orders`、`/raw-records`、`/reports`、`/payment-receipts`、`/green-channel-requests`、`/change-requests`、`/sample-retentions`、`/report-templates`。
- 工作中心、报告注册中心、设备、导入导出等资源返回 403，说明部分权限已处理，但不是全局一致。
- `portal.applicant` 调用 `/submissions` 返回 10 条记录，且其中多条 `customerOrgId` 不同于该用户 `/auth/me` 的 `customerOrgId=00000000-0000-0000-0000-000000000301`。如果这些记录确实属于同一申请人跨单位创建，需要代理授权或明确规则；否则存在客户数据隔离风险。

缺口：

- 后端按 `clientType=PORTAL` 统一拒绝内部资源。
- 客户数据过滤应同时校验 `customerOrgId`、`applicantUserId`、授权项目和代理关系。
- API 不应以“空数据”替代权限拒绝；无权限应返回 403。

## 5. 内部端缺口

### 5.1 内部管理员

应有能力：

- 系统管理员应维护组织、用户、角色、字典、节假日、系统配置。
- 质量管理员应查看质量相关资源、报告模板、设备文件、报告注册中心、导入导出等。

实测现状：

- `internal.admin` 登录成功，角色显示 `QUALITY MANAGER`、`SYSTEM ADMIN`。
- 左侧菜单只有“工作中心”。
- 没有主数据、系统配置、用户、角色、组织架构、字典、节假日、报告模板、导入导出、审计日志入口。

缺口：

- 补齐 `InternalMainData`、`InternalSystemConfig`、`InternalReportTemplates`、`InternalImportExportTasks`、`InternalReportRegistry` 等页面。
- 系统管理员不默认拥有业务审批权，但必须拥有系统配置和账号维护能力。
- 质量管理员需要质量监督类查询和模板发布能力。

### 5.2 内部销售

应有能力：

- 业务员可进行送检受理、报价发起、合同发起、进度沟通。
- 能查看自己负责客户和项目。

实测现状：

- `internal.sales` 登录后只看到“工作中心、送检受理、项目详情”三个菜单。
- 点击“送检受理”后只出现入口卡片，没有真实送检单列表。
- 点击“项目详情”后仍是入口卡片，没有项目详情。
- “进入”按钮点击后页面无明显跳转。

缺口：

- 送检受理列表需要展示客户提交的 `SUBMITTED` 送检单，支持完整性核验、受理、驳回、拆分项目。
- 项目详情需要显示项目类型、资质类型、非标评审、报价、合同、样品、方案、工单、报告、付款、归档状态。
- 销售端需要报价和合同入口，否则不能完成主流程前半段。

### 5.3 工作中心

应有能力：

- 项目健康度、当前卡点、责任链、人员负荷、时间趋势、我的待办。
- 结构化阻塞创建、更新、关闭。
- 默认筛选：我的待办、我负责的项目、超期项目、预警项目、风险项目、非标评审中、报告审核中、付款锁定。

实测现状：

- 页面结构存在，显示正常/预警/风险项目、我的待办、超期任务、项目健康度、当前阻塞、人员负荷、趋势指标。
- 所有核心数据为 0 或 No data。
- 筛选只有“风险、预警、超期、正常”。
- 未看到新增阻塞、关闭阻塞、Owner 变更、协作人、预计恢复时间等操作。

缺口：

- 工作中心需要绑定真实项目、工单、报告、付款门禁和阻塞数据。
- 增加阻塞管理入口，字段必须覆盖 `blockerType`、`severity`、`description`、`impactScope`、`expectedRecoveryAt`、`ownerUserId`、`status`、`resolution`。
- 增加项目 Owner、协作人、上级抄送和通知规则。
- 增加趋势快照生成逻辑，而不是仅返回 0。

## 6. 主流程逐段缺口

### 6.1 客户、委托单位和门户账号

应有能力：

- 管理委托单位、联系人、报告和发票信息。
- 内部创建或邀请客户门户账号。
- 客户单位管理员管理本单位账号。

实测现状：

- `GET /customer-orgs` 返回 404。
- `GET /portal-users` 返回 404。
- 前端未看到客户单位、联系人、门户账号管理页面。

缺口：

- 补齐客户单位、联系人、制造商、门户账号 API 和页面。
- 客户门户应允许维护委托单位基础信息，但受权限控制。

### 6.2 送检与内部受理

应有能力：

- 客户提交送检信息。
- 内部核验完整性。
- 信息不完整时不得进入报价或合同。
- 支持无样受理。

实测现状：

- `GET /submissions` 可用，销售账号返回 7 条，门户账号返回 10 条。
- 客户门户 UI 未提供正式提交入口。
- 内部销售 UI 未提供送检单列表和受理操作。
- `POST /submissions` 对空请求可返回 400，说明创建接口有基本校验。
- `POST /submissions/{id}/accept` 对销售账号返回 403，当前销售账号无法执行文档定义的受理动作。

缺口：

- 打通“客户保存草稿 -> 提交 -> 内部待受理 -> 受理通过/退回补充”状态流。
- 明确销售、样品管理员、技术负责人在受理环节的权限。
- 受理页面需要支持完整性检查、项目类型初判、附件查看、退回原因。

### 6.3 项目类型判断和项目拆分

应有能力：

- 标准方法 + 有 CMA/CNAS 资质。
- 标准方法 + 无 CMA/CNAS 资质。
- 非标方法 / 客户提供方法。
- 一个送检单可拆分为多个项目。

实测现状：

- `GET /projects` 返回 404。
- 内部端没有项目列表或项目详情。
- `POST /submissions/{id}/split-projects` 对销售账号返回 403。
- 现有送检单数据没有形成项目、样品、方案、工单、报告链路。

缺口：

- 补齐项目实体 API、列表、详情、状态机。
- 送检单拆分项目要能复制客户、制造商、样品、GLP、检测项目等信息。
- 项目类型和资质类型必须结构化，不能只存在备注。

### 6.4 非标方法报价前评审

应有能力：

- 非标申请 → 技术评审 → 成本评估 → 周期评估 → 技术负责人审批 → 业务负责人审批 → 允许报价。
- 未审批通过前禁止正式报价、合同签署和试验流程。

实测现状：

- 没有非标评审 UI。
- `GET /projects` 缺失导致无法查询或推进非标项目。
- 相关动作接口存在权限校验，但没有可操作项目和评审详情页。

缺口：

- 增加非标评审页，结构化记录方法来源、方法文件、风险、设备、动物、耗材、标准品、分包、人力成本、材料成本、周期等。
- 增加技术负责人和业务负责人审批记录。
- 在报价、合同、试验下发接口上实现后端门禁。

### 6.5 报价、合同和协议

应有能力：

- 报价管理。
- 合同、协议、合同评审。
- 补充合同或补充协议。
- 三类项目走不同报价、合同、报告声明、签章和归档规则。

实测现状：

- `GET /quotations` 返回 404。
- `GET /contracts` 返回 500。
- 内部端没有报价、合同、协议、合同评审页面。
- 客户门户没有协议确认或签署入口。
- `GET /report-templates` 返回 200 但 total=0，没有模板数据。

缺口：

- 补齐报价单、报价明细、报价状态和审批记录。
- 修复合同列表 500。
- 增加合同/协议模板、签署文件、合同评审结构化字段和补充协议关联。
- 客户门户增加协议确认/签署。
- 三类项目模板路由和报告声明必须落地。

### 6.6 样品接收、拍照、标签、入库和流转

应有能力：

- 样品到达登记、核验、异常、照片、标签、预入库、正式入库。
- 样品未到时禁止试验下发、置样、结果录入和报告签发。

实测现状：

- `GET /samples` 对管理员、销售、门户均返回 403。
- 内部菜单没有样品收样台，因当前测试账号没有 `SAMPLE_MANAGER`。
- API 存在 `POST /samples/{id}/receive` 和 `POST /samples/{id}/stock-in`，但无法基于实际样品验证。
- 前端源码中可见样品收样台结构，但当前账号无法进入，且样品列表无数据可验证。

缺口：

- 提供样品管理员测试账号并验证收样台。
- 样品列表需要从受理后项目生成。
- 增加样品照片上传、标签打印、异常退回、预入库、正式入库和流转记录。
- 后端必须阻止未核验样品进入试验下发。

### 6.7 置样、方案编制、审批和试验计划

应有能力：

- 方案编制可在无样状态下进行，但正式试验下发前必须完成样品核验。
- 所有项目必须走 SD。
- GLP 项目必须走 QA。
- 动物试验必须走伦理委员会。
- 资料不全时只能形成待下发任务，不能生成可执行工单。

实测现状：

- `GET /study-plans` 返回 200 但 total=0。
- 内部端没有方案与试验计划页面。
- `portal.applicant` token 调用 `/study-plans` 也返回 200 空数据，不符合门户权限边界。

缺口：

- 增加方案编制页，包含检测依据、判定依据、人员、设备、试剂、标准品、周期、原始记录模板和报告模板。
- 增加 SD/QA/伦理审批。
- 增加待下发和可下发状态区分。
- 后端 dispatch 必须校验合同、样品、置样、审批和伦理。

### 6.8 试验执行、结果录入和原始记录

应有能力：

- 任务领取、领样登记、开始、暂停、继续、完成。
- 环境条件、仪器设备、标准品、试剂、耗材使用记录。
- 原始记录上传或在线填写。
- 结果录入、结论填写和原始记录复核。

实测现状：

- `GET /work-orders`、`GET /raw-records` 返回 200 但 total=0。
- 内部端没有工单执行页和原始记录页面。
- 门户 token 访问 `/work-orders`、`/raw-records` 返回 200 空数据，应禁止。

缺口：

- 增加工单执行页和检测员工作台。
- 增加领样、设备、环境、试剂、标准品、耗材记录。
- 增加原始记录模板渲染、附件上传、审核退回、审核通过。
- 原始记录审核人不能与检测人相同的规则需要实现。

### 6.9 报告生成、审核、签发和发放

应有能力：

- 基于送检、合同、样品、检测项目、原始记录和报告模板生成草稿。
- 报告审核固定为 QC → QA → SD → 授权签发。
- 未付款时允许草稿预览，禁止正式 PDF 下载、电子签章发放、纸质报告打印和样品退还。
- 首个自动生成试点为无菌检查报告。

实测现状：

- `GET /reports` 返回 200 但 total=0。
- `GET /report-registry/search` 管理员返回 200 但 total=0。
- 客户门户没有报告草稿预览和正式报告下载页面。
- 内部端没有报告编制、审核、签发页面。
- `GET /report-templates` 返回 total=0，未注册报告模板。

缺口：

- 注册报告模板，至少完成无菌检查试点模板。
- 增加报告草稿生成、字段映射、人工编辑、版本锁定。
- 增加 QC、QA、SD、授权签发审批链。
- 增加客户草稿预览水印和正式报告下载付款门禁。
- 增加报告版本、发放日志、重新签发和作废流程。

### 6.10 付款控制和绿色通道

应有能力：

- 收款记录作为独立实体。
- 财务登记到账后自动解锁报告和样品处置。
- 绿色通道需部门负责人和管理层审批，只解锁电子正式报告。

实测现状：

- `GET /payment-receipts` 返回 200 但 total=0。
- `GET /green-channel-requests` 返回 200 但 total=0。
- 内部端没有财务收款或绿色通道页面。
- 门户 token 访问付款和绿色通道资源返回 200 空数据。

缺口：

- 增加财务收款登记、凭证附件、冲销、汇总付款状态。
- 增加报告和样品处置的后端付款门禁。
- 增加绿色通道申请、两级审批、解锁范围、发放日志和归档。

### 6.11 设备预约和设备文件

应有能力：

- 半小时粒度预约。
- 检测员提前 7 天，外部用户提前 2 天。
- 内部预约可覆盖外部预约，必须记录原因并通知。
- 设备文件绑定设备详情，包含证书、SOP、维护和校准资料。

实测现状：

- `GET /devices` 管理员返回 200 但 total=0。
- `GET /device-bookings` 返回 404。
- `POST /device-bookings/{id}/override` 返回 404。
- 前端没有设备预约日历和设备文件页面。

缺口：

- 补齐设备台账种子数据。
- 补齐设备预约 API、日历 UI、半小时粒度、冲突校验、覆盖原因、通知和待重约状态。
- 补齐设备文件上传、有效期、当前有效标记和到期预警。

### 6.12 标准品、耗材和库存

应有能力：

- 标准品和耗材台账、库存、有效期、领用、预警、基础出入库。
- 支持按有效期、库存下限、开瓶日期、存储条件提醒。

实测现状：

- `GET /inventory-batches` 返回 404。
- `GET /inventory-transactions` 返回 404。
- 前端没有库存管理页面。

缺口：

- 补齐库存批次、库存流水 API 和页面。
- 增加入库、出库、领用、退回、报废、库存调整。
- 增加有效期预警、低库存预警和工作中心提醒。

### 6.13 统一变更中心

应有能力：

- 协议、样品、项目、报告关键字段变更统一落到 `change_request`。
- 字段级 diff、变更原因、附件、审批、生效、审计、归档。

实测现状：

### 6.14 留样管理

缺口：

- 需要提供 MinIO 测试账号或应用侧文件接口。
- 验证模板文件、样品照片、原始记录、报告 DOCX/PDF、付款凭证、归档文件是否真实进入对象存储。

- 验证正式报告下载、批量下载和归档是否通过受控接口访问对象，不直接暴露对象地址。

## 10. 可验收的下一轮测试脚本目标

下一轮补齐开发后，建议至少能完成以下端到端脚本：

1. 客户登录门户，填写 Ver.15 送检单，保存草稿，正式提交。
2. 销售登录内部端，看到该送检单，完成受理和项目拆分。
3. 对标准项目生成报价和合同，完成签署确认。
4. 样品管理员登记样品到达、上传照片、核验通过、正式入库。
5. 技术或 SD 编制方案，完成必要审批。
6. SD 下发试验计划，检测员领取工单并录入结果和原始记录。
7. 原始记录审核通过后生成报告草稿。
8. 报告完成 QC、QA、SD、授权签发。
9. 未付款时客户只能在线预览带水印草稿，不能下载正式 PDF。
10. 财务登记到账后客户可下载正式报告，下载写入发放日志。
11. 项目自动生成归档项，工作中心健康度和趋势有真实数据。
