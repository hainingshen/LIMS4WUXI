# 现有系统复用与重做策略

## 1. 目的

现有 LIMS 用户手册中已经包含协议管理、样品流转单、工单、报告、检测项目、样品入库、标准品和设备等功能。新系统不应忽略这些材料，但也不能简单照搬，因为客户已经明确提出现有系统存在统计、进度、工作中心、报告生成和主流程协同不足。

## 2. 模块策略

| 现有模块 | 现有能力 | 新系统策略 |
| --- | --- | --- |
| 协议管理 | 新建、编辑、查看协议，部分字段已具备 | 重写流程，复用字段含义和历史数据 |
| 协议变更申请 | 对已建协议发起变更 | 不单独照搬菜单，纳入统一变更中心，以 `targetType=CONTRACT` 区分 |
| 样品流转单 | 样品基础信息、检测信息、报告审批记录 | 保留“流转单”概念，重构为项目-样品-工单链路 |
| 样品变更申请 | 对样品基础信息或检测信息发起变更 | 不做孤立模块，纳入统一变更中心，以字段级变更、审批和生效留痕处理 |
| 留样管理 | 留样列表、留样信息和处置 | 保留业务价值，重做为 `sample_retention` 独立生命周期 |
| 工单管理 | 根据样品检测项目自动生成工单，一个工单对应一个检测项目 | 复用核心规则，补充 Owner、进度、阻塞、负荷 |
| 领样登记 | 工单阶段可领样，记录样品序号、领样人、时间 | 复用规则，纳入样品流转和审计 |
| 工单执行 | 开始、结束、子项完成后工单结束 | 重写状态机，增加暂停、结果录入、原始记录审核 |
| 报告编制 | 工单结束后生成报告，选择模板，在线编辑 | 复用模板思路，重写为 QC → QA → SD → 签发 |
| 报告下载 | 测试版和正式版以水印区分 | 保留水印规则，增加付款门禁和草稿在线预览 |
| 报告模板管理 | 多类 Word/报告/协议模板维护 | 保留模板资产，重做版本、分类、自动化等级和发布控制 |
| 报告数据中心 | 历史报告检索和查看 | 不做报告副本库，重做为报告注册中心，汇总报告版本、发放日志和档案 |
| 检测子项 | 标准化操作单元，可发布/取消发布 | 保留三层模型，作为新系统检测配置基础 |
| 检测标准 | 标准化参考体系 | 迁移并清洗，关联资质范围 |
| 检测项目 | 全流程技术方案，包含多个检测子项 | 保留模型，补充项目类型和资质属性 |
| 样品入库 | 待编号阶段入库并自动编号 | 重写接收、拍照、预入库、正式入库、异常处理 |
| 标准品管理 | 入库、库存、预警 | 复用基础字段，重写为批次和流水模型 |
| 仪器设备 | 设备台账 | 迁移台账，补充预约日历 |
| 设备文件管理 | 设备说明书、校准、维护等文件管理 | 不做独立文件柜，嵌入设备详情和设备台账，证书有效期进入预警 |
| 角色和字典 | 已有角色、系统字典 | 迁移基础数据，按新审批角色重配 |
| 组织架构、用户、节假日 | 组织、账号、日历基础管理 | 保留管理能力，重做权限边界和审计，节假日参与 SLA 计算 |
| 导入导出 | 列表导出和历史数据处理 | 重做为受控异步任务，预校验、结果文件、过期和审计必须完整 |
| 工作中心 | 有入口但可视化不足 | 重写，按健康度、阻塞、Owner、趋势设计 |

## 3. 迁移策略

现有系统数据迁移时，应优先保留以下旧系统编号：

- 协议编号。
- 样品流转单编号。
- 工单编号。
- 样品编号。
- 报告编号。
- 检测项目编号。
- 检测标准编号。
- 检测子项编号。
- 设备编号。
- 标准品编号。
- 留样编号或旧留样记录标识。
- 报告模板名称和版本。
- 设备文件名称、证书编号和有效期。

旧编号写入 `legacy_id` 或专门的历史编号字段，不覆盖新系统 UUID 主键。

## 4. 重做优先级

优先重写：

- 非标报价前评审。
- 工作中心。
- 报告审核和付款门禁。
- 样品接收与异常处理。
- 统一变更中心。
- 留样生命周期。
- 报告注册中心和报告模板版本管理。
- 导入导出任务和迁移预校验。
- 数据迁移和字段清洗。

可借鉴复用：

- 检测项目、检测标准、检测子项三层模型。
- 工单由检测项目生成的规则。
- 报告模板选择和水印区分。
- 标准品库存预警。
- 设备台账字段。

## 5. 不照搬旧菜单的设计原则

现有系统菜单结构可以帮助确认业务对象，但不直接决定新系统导航。判断是否照搬菜单时按以下原则：

- 如果旧功能只是同一类变更的不同入口，例如协议变更和样品变更，合并为统一变更中心。
- 如果旧功能是主对象的附件能力，例如设备文件，嵌入主对象详情，不再做孤立文件柜。
- 如果旧功能是查询视角，例如报告数据中心，重做为注册中心或列表筛选，不复制一套报告数据。
- 如果旧功能存在合规价值，例如留样、模板版本、发放日志，独立建模并纳入审计。
- 如果旧功能只是批量操作入口，例如导入导出，必须受控异步化，避免绕过权限和审计。

## 6. 一期功能覆盖判断

按只读盘点结果和当前一期设计，功能覆盖分为三类：

| 分类 | 功能 | 处理结论 |
| --- | --- | --- |
| 已覆盖并增强 | 委托单位、协议/合同、检测目录、样品、工单、设备台账、标准品库存、报告审核、工作中心 | 在新流程中重写，补充审批、状态机、付款门禁和可视化 |
| 已补足设计但需进入开发契约 | 统一变更中心、留样管理、报告注册中心、报告模板分级、设备文件、导入导出任务、旧状态映射 | 已在 Markdown 设计中补齐，开发前需按 Goal 允许补 `openapi.yaml`、权限矩阵和字典 |
| 超出现有系统 | 客户门户、非标报价前评审、绿色通道、付款门禁、报告草稿在线预览、动态表单、迁移质量评分 | 保留为一期差异化能力，不应因为旧系统没有而删除 |

仍不建议一期完整复制的能力：

- 客户门户自助变更申请。当前应先提供内部统一变更中心，客户自助变更需等门户权限和变更规则稳定后开放。
- 设备自动采集、自动实验排程、ERP 集成、采购和供应商协同。它们不是旧系统核心迁移门槛，且一期实施风险高。
